# 改善ループ

よろずやは「使う → 気づく → 記録する → 直す → 再発を防ぐ → 振り返る」を回して育てます。
人が回しても、AI エージェントが回しても同じ手順になるよう、段階ごとに置き場所と道具を決めています。

```
   ┌──────────── 使う（手元のアプリ・Storybook・LP）
   │                    │ 気づく
   │                    ▼
   │   ┌─ 自動: make check / CI ─┐   ┌─ 手動: Issue「改善提案」・会話 ─┐
   │   └───────────┬────────────┘   └───────────────┬──────────────┘
   │               ▼                                 ▼
   │          docs/improvement/backlog.md（改善候補）
   │                    │ 直す（1 PR 1 改善）
   │                    ▼
   │   再発防止: lint ルール / 境界検査 / 型 / テスト / play / ルール文書 / ADR
   │                    │
   └──── docs/improvement/log.md に記録 ◀┘
```

## 1. 気づく

### 自動

| 仕組み            | タイミング                | 何を見つけるか                                                                                                |
| ----------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `make typecheck`  | コミット前・PR ごと（CI） | 型の誤り。項目の説明や対応表を `Record<型, …>` で持たせ、項目の書き漏れも型で検出する                         |
| `make lint`       | コミット前・PR ごと（CI） | Oxlint（`Result` の握りつぶし、マイグレーション以外の `CREATE TABLE` など）と境界検査（`make lint-boundary`） |
| `make fmt`        | コミット前・PR ごと（CI） | フォーマットのずれ                                                                                            |
| `make test`       | PR ごと（CI）             | 振る舞いの退行（Vitest）、ストーリーの `play`（`src/components/stories.test.tsx` に登録したもの）             |
| `make test-e2e`   | PR ごと（CI）             | 画面を通した操作の退行（Playwright）                                                                          |
| `make site-build` | 手元で都度                | デモが描画できない・撮影できないこと（失敗時はスクリーンショットと原因を出す）                                |

### 手動

使っていて気づいたことは、GitHub の Issue テンプレート「改善提案」で起票するか、エージェントとの会話で伝えます。
どちらも最後は `docs/improvement/backlog.md` に 1 行で残します。

## 2. 記録する

改善候補は [`improvement/backlog.md`](./improvement/backlog.md) にまとめます（Issue があればリンク）。優先度は次の順で判断します。

1. データを失う・壊す（保存・読み込み・マイグレーション・インポート）
2. 設計のルールの破れ（[`rules/security.md`](../rules/security.md)：ローカル完結、境界、`Result`）
3. 提出物の品質（スキルシートの見た目・改ページ・印刷、採用担当者の読みやすさ）
4. 開発体験（コマンド、検査、ドキュメント、エージェントの手順）
5. 見た目の好み

## 3. 直す

- 1 PR 1 改善。大きいものは分割し、残りをバックログに戻す
- 修正は PR で行い、PR テンプレートのチェックリストを満たす
- 機能を足す・大きく変えるときは、先に `docs/specs/` に指示書を書く
- 値や方針を変えたら ADR を足す（[`decisions/`](./decisions/README.md)）
- スキーマを変えたら `make db-generate` でマイグレーションを作る
- 画面や LP を変えたら、必要に応じて `make site-build` → `make site-publish` で公開サイトを撮り直す（`.claude/skills/publish-site/SKILL.md`）

## 4. 再発を防ぐ（いちばん大事）

**直しただけで終わらせない。** 同じ種類の問題が二度と起きないよう、次のどれかを必ず足します。

| 問題の種類                                     | 足すもの                                                                                 |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------- |
| import の向き・データベースの扱いの破れ        | `eslint.config.js` か `scripts/check-advanced-boundaries.mjs` に規則を足す               |
| lint で見つけられる書き方の問題                | `vite.config.ts` の `lint` に規則を足すか、`oxlint-plugins/` にプラグインを足す          |
| 項目の足し忘れ（説明・表示・入出力の対応漏れ） | 対応表を `Record<型, …>` にして型で網羅させる                                            |
| 振る舞いの不具合                               | 対象の隣に `*.test.ts(x)`、画面ならストーリーの `play`、操作の流れなら `tests/*.spec.ts` |
| JSON・データベースの互換                       | 古い版を読み込むテスト（例: `sheet-file.test.ts` の版 1 の読み込み）                     |
| 判断基準のあいまいさ                           | `rules/security.md`・`AGENTS.md`・`COMPONENT_STRUCTURE.md` に追記、または ADR            |
| 手順の抜け・やり直し                           | `Makefile` のコマンドか `.claude/skills/` のスキルに手順を足す                           |

どうしても仕組みにできないときは、`log.md` の「再発防止」に「—」と書き、理由をバックログに残します。

## 5. 振り返る

[`improvement/log.md`](./improvement/log.md) に 1 改善 1 行で記録します（新しいものを上に）。
ときどきログを見返し、同じ種類の改善が続いていれば、ルール文書や検査の仕組みそのものを見直します。見直した結果は ADR に残します。

## AI エージェントが回す場合

手順は [`.claude/skills/improve/SKILL.md`](../.claude/skills/improve/SKILL.md) にまとめています。エージェントは次の順で動きます。

1. `docs/improvement/backlog.md` と未解決の Issue を読み、優先度の高いものを 1 つ選ぶ（頼まれたものがあればそれ）
2. 関連する指示書・ADR・ルールを読んでから直す
3. 上の「再発を防ぐ」に従って検査やテストを足す
4. `make check` が通ることを確かめ、`log.md` に 1 行足し、バックログから消して PR を出す

会話で指摘を受けて直したときも同じです。指摘の内容は `log.md` に残し、同じ指摘を二度受けないよう再発防止を足します。
